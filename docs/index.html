01 / ABOUT THE PROJECT

A small engine.
A complete learning loop.

ENGINEERING NOTE / WHY THIS EXISTS

Built to understand what happens between an editor and a running game.

SDL2 Game Engine is a focused, independently developed 2D C++ engine and editor. Rather than hide the underlying systems, it connects scene editing, asset libraries, physics, animation, sound and scripting in one codebase.

The emphasis is on a usable foundation: create objects in the editor, save a scene, and load that scene in a separate game build. It is a compact project for experimentation and learning—not a replacement for a full production engine.

Native C++ Windows x64 Visual editor Readable systems
BUILT FOR Small 2D experiments Scenes, assets, behavior, builds
DESIGN CHOICE Separate editor & runtime Debug tools stay out of the game build
CURRENT FOCUS Working foundation Deliberately limited scope

Scripts bridge the systems. ScriptContext provides access to services such as animation and audio. C++ scripts are compiled into the program; adding new ones requires rebuilding.

DESIGN / A

One asset, many consumers

Animation and audio live in shared manager libraries, not only inside individual GameObjects. Scripts can reference assets even when no object currently uses them.

DESIGN / B

Saving more than objects

Scene serialization includes asset paths and identifiers so loading can restore the reusable libraries before scripts execute.

DESIGN / C

Two faces of one engine

The same codebase has editor-oriented Debug builds and game-oriented Release builds, separated by compile-time definitions.

GUIDE 01 · FIRST RUN

From source to editor.

Use a Windows machine with Visual Studio, the MSVC C++ toolchain and x64 build support. Open GameEngine.slnx from the repository root—or use the supplied batch scripts.

PowerShell — clone 
git clone https://github.com/mert-akif/SDL2GameEngineish.git
cd SDL2GameEngineish
  1. Open GameEngine.slnx in Visual Studio.
  2. Select Debug and x64 , then build.
  3. Launch the editor and create a GameObject.
  4. Save the scene before making a Release build.
Included dependencies. This project keeps native SDL2 and Box2D packages alongside the source. If linking fails, check the selected x64 configuration and package paths before copying random DLLs.

GUIDE 03 · DATA

Keep references portable.

The scene format stores reusable asset metadata alongside objects. The loader resolves assets before dependent animations and scripts are attached.

Conceptual scene excerpt 
TextureAsset
key=player
path=Assets/Textures/player.png
EndTextureAsset

GameObject
id=0
name=Player
textureKey=player
End

Use project-relative paths , such as Assets/Textures/player.png , rather than paths pointing to a specific Windows account. Store common animation clips and sound IDs in global manager data.

Illustrative snippet. A complete scene also includes whichever object and asset properties your serializer writes.
GUIDE 04 · BEHAVIOR

C++ scripts, connected to the engine.

Behavior is implemented with C++ script classes. The engine's ScriptRegistry connects named scripts to GameObjects, while ScriptContext supplies access to engine services.

REGISTER Make it discoverable

Define the script class and register it with the registry.

ATTACH Choose per object

Assign the registered script through the editor.

RUN Use engine services

Manage animation and sound using the IDs configured in the editor.

REBUILD Compile new C++

New scripts become available after rebuilding and restarting.

Not hot-reload scripting. Scripts compile into the application; the engine does not interpret scripts dynamically at runtime.
GUIDE 05 · DISTRIBUTION

One source tree. Two modes.

DEBUG / EDITOR Develop and inspect

Builds include the Dear ImGui editor for manipulating scene data.

RELEASE / GAME Play the saved scene

The game build loads the serialized scene without editor panels.

PowerShell — from repository root 
cd GameEngine\Build
.\build-debug.bat
.\run-debug.bat
.\build-release.bat

Run scripts while the current directory is GameEngine/Build , unless you have updated them to resolve paths relative to their own location. Verify the output contains required SDL DLLs and your Assets folder.

Scope. Windows x64 is the documented build target. Other platforms are not advertised as supported builds.

09 / COMMON QUESTIONS

Good questions.
Useful answers.

Most first-run problems come down to missing native libraries, working directories, or the difference between editing a scene and loading it in a game build.

Open GitHub issues ↗
Why does the Release build show an empty scene? +

The default Main.scene can be empty. Create and save objects in the editor before building the game, and confirm the scene and assets are copied into the release output.

What if SDL2.lib or Box2D.lib cannot be found? +

Check your build configuration (Debug/Release, x64), the native package folders and the linker paths. Native .lib files and runtime DLLs are different: you may need both when building and launching.

Can I add scripts without rebuilding? +

No. Behavior scripts are C++ classes compiled into the engine. After creating and registering a new class, rebuild the editor/game so the executable includes it.

Are animation and sound tied to a GameObject? +

Assets are stored in global manager libraries. GameObjects and scripts reference them by ID or key. This allows scripts to use a sound or animation even without an existing object assignment.

Does the engine support Linux or macOS? +

The documented and tested setup is Windows x64 with Visual Studio and the MSVC toolchain. The code uses portable libraries, but other platform builds are not currently documented or guaranteed.

Is this intended for production-scale games? +

It is a lightweight, focused engine foundation designed for learning, small prototypes and understanding engine architecture. It intentionally does not claim the feature breadth or testing of mature engines.
